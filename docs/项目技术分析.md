# SuperMew 项目技术分析

## 一句话定位

一个从零构建的全栈 RAG 知识库问答系统，核心聚焦混合检索、查询重写、流式推理与实时可观测性。

---

## 技术亮点

### 1. 混合检索体系：Dense + Sparse + RRF 融合 + Rerank 精排

- 稠密向量采用本地 `BAAI/bge-m3`（`langchain_huggingface`），稀疏向量**手写 BM25**（中英混合规则分词 + IDF 计算 + 词表/DocFreq 持久化到 `bm25_state.json`），而非调包
- 通过 Milvus `AnnSearchRequest` 双路并发检索 + **RRF (Reciprocal Rank Fusion)** 排序（k=60），避免了传统加权求和中 α 参数调优的困难
- 两条召回路径都经过 **Jina Rerank API 精排**，Rerank 分数可在前端可视化
- 实现了完整的**双向降级策略**：Hybrid 失败 → 纯 Dense 兜底，Rerank 失败 → 用 RRF 排名兜底，Rerank 未配置 → 优雅跳过

### 2. 三级滑动窗口分块 + Auto-Merging（Leaf-Only 向量化）

- 用 `RecursiveCharacterTextSplitter` 实现 L1(大) → L2(中) → L3(小) 三层嵌套分块，通过 `chunk_id / parent_chunk_id / root_chunk_id` 维护层级关系
- **仅叶子层 (L3) 写入 Milvus**，L1/L2 父块存入 PostgreSQL + Redis 缓存，减少向量存储冗余约 2/3
- 检索时优先召回 L3 叶子，**同一父块下 ≥2 个叶子命中则自动合并为父块**（L3→L2→L1 两段合并），兼顾精细匹配与完整上下文

### 3. 查询重写体系（LangGraph 状态机）

- 基于 `LangGraph StateGraph` 构建 RAG 工作流：检索 → 相关性评分门控 → 重写/直接回答 → 扩展检索
- **结构化输出的路由选择**：Step-Back Prompting（生成退步问题 + 答案）、HyDE（生成假设性文档）、Complex（两者结合），由 LLM 根据问题类型自主决策策略
- 相关性评分用独立 grader model（`gpt-4.1`，structured output `yes/no`），不满足则自动触发重写检索
- 扩展检索结果自动去重（按 `(filename, page, text)` 三元组）

### 4. 实时 RAG 思考链路可视化（跨线程事件穿透）

- **核心难题**：FastAPI 单线程 asyncio event loop 中，同步 RAG 工具运行在 `ThreadPoolExecutor` 子线程，无法直接访问主线程 `asyncio.Queue`
- **解决方案**：`Global Loop Capture + call_soon_threadsafe` 模式 —— 主线程启动 Agent 前捕获 `asyncio.get_running_loop()`，RAG 工具在子线程通过 `loop.call_soon_threadsafe(queue.put_nowait, step)` 注入事件
- Agent 流式循环运行在 `asyncio.create_task` 后台任务中，主循环只从统一 `output_queue` 取事件 yield SSE，**实现了工具执行期间（Searching → Grading → Rewriting）的实时推送**，而非等待工具完成后再展示
- 前端用**微型状态机**（Idle → Thinking(Active RAG) → Streaming）管理 SSE 事件流，思考气泡与回答气泡合二为一无缝切换

### 5. 流式输出 + 回答终止

- 后端基于 `agent.astream(stream_mode="messages")` 逐 token 产出，过滤 `tool_call_chunks`，通过 `StreamingResponse(media_type="text/event-stream")` 推送
- **显式取消机制**：捕获 `GeneratorExit`（客户端 AbortController 断开时触发）→ 主动 `agent_task.cancel()` → 注入 `CancelledError` 关闭 httpx TCP 连接 → 服务端检测掉线后停止推理，实现**真正的 Token 节省**

### 6. BM25 统计持久化与增量更新

- 手写 BM25 而非调库：`vocab`（词→稀疏维度下标）、`doc_freq`（词→文档频次用于 IDF）、`total_docs / sum_token_len / avg_doc_len` 全量持久化到 JSON 文件
- 入库时增量 `increment_add`，删除/覆盖文档前按文件名从 Milvus 分页拉取全部 chunk 文本后增量扣减
- 词表下标不回收（避免与历史稀疏向量维度冲突），写入与检索共用 `embedding_service` 单例

### 7. 完整后端工程体系

- **认证鉴权**：JWT + RBAC（admin/user），admin 邀请码模式，PBKDF2-SHA256 密码哈希 + 兼容历史 bcrypt
- **数据持久化**：SQLAlchemy ORM（User / ChatSession / ChatMessage / ParentChunk），PostgreSQL 存储
- **缓存策略**：Redis 按 user+session 维度缓存消息、按 user 维度缓存会话列表、按 chunk_id 缓存父级分块，写入/删除后主动失效
- **会话记忆**：消息超 50 条自动触发 LLM 摘要压缩注入 SystemMessage

| 层级 | 技术选型 |
|------|----------|

## RAG 全链路流程

```
用户提问
  │
  ▼
retrieve_initial ──► L3 Milvus Hybrid 检索 (Dense + Sparse + RRF)
  │                   → Jina Rerank 精排
  │                   → Auto-Merging (L3→L2→L1)
  ▼
grade_documents ────► yes ──► 生成最终回答
  │
  │ (no)
  ▼
rewrite_question ──► 路由选择: Step-Back / HyDE / Complex
  │                   → 生成退步问题 / 假设性文档
  ▼
retrieve_expanded ─► 多路扩展检索 → 去重 → 生成最终回答
```

## 核心架构

```
POST /chat/stream → StreamingResponse(text/event-stream)
  │
  ▼
chat_with_agent_stream()
  │
  ├── 创建统一输出队列 (asyncio.Queue)
  ├── 设置 _RagStepProxy → emit_rag_step() 的输出直接入队
  ├── 启动 _agent_worker 后台任务 (asyncio.create_task)
  │     └── agent.astream(stream_mode="messages") 逐 token 产出
  │           ├── AIMessageChunk (文本) → {"type": "content"} 入队
  │           └── tool_call_chunks (工具调用) → 跳过
  │
  └── 主循环：await output_queue.get() → yield SSE
        ▲
        │ (并发) RAG 工具在线程池中执行
        │ emit_rag_step() → loop.call_soon_threadsafe → 入队
        │ {"type": "rag_step"} 立即从队列取出并推送到前端
```

## 文档入库链路

```
上传 PDF/Word/Excel
  │
  ▼
检查同名文件 → 按文件名从 Milvus 分页拉取 chunk 文本
  │            → BM25 increment_remove 扣减统计
  │            → 删除旧向量 + 父块缓存
  ▼
DocumentLoader 三级滑动窗口分块
  │
  ├── L1/L2 父级分块 → ParentChunkStore (PostgreSQL + Redis)
  │
  └── L3 叶子分块 → BM25 increment_add (更新 N/df/长度)
                    → Dense + Sparse 向量生成
                    → Milvus 入库
```
